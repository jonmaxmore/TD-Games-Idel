# SPEC: ศึกกับเพื่อน (ห้องเพื่อนด้วยรหัสห้อง)

> สถานะ: สร้างแล้ว รันในเครื่องเท่านั้น ยังไม่ deploy (เจ้าของตัดสิน 2026-11-08: PvP เริ่มจากห้องเพื่อน ส่วนโฮสต์และค่าใช้จ่ายจะเสนอแยก)
> โค้ด: `packages/protocol` (ข้อความและการตรวจ), `packages/game` (เซิร์ฟเวอร์), `packages/client/src/pvp.ts` และ `net.ts` (หน้าจอ)
> อ้างอิง: [SPEC-castle-battle.md](SPEC-castle-battle.md) §8 และ §14, [matchmaking.md](../design/matchmaking.md) §8, [architecture.md](../design/architecture.md), ADR 0003 และ 0007

## 1. เป้าหมาย
- ผู้เล่นสองคนเล่นศึกชิงเมือง 1v1 กันได้จริงผ่านเซิร์ฟเวอร์ โดยเซิร์ฟเวอร์เป็นผู้ตัดสินผล
- วางฐานที่ ranked และ matchmaking ใน M1–M2 ใช้ต่อได้: กฎชุดเดียว (`packages/sim`), lockstep, รีเพลย์, ตรวจ desync

## 2. กติกาของศึก
- ใช้กติกาศึกฝีมือ: `normalized: true` การ์ดทุกใบค่าพื้นฐาน มือเลือกเองจากการ์ดทุกใบ (`rankedPool`) ภายใต้งบแต้ม (SPEC-deck-budget) ข้อความ `team` คือ `{ leader, sub, picks }` และเซิร์ฟเวอร์ตรวจด้วย `validateDeck` ทัพที่ไม่ถูกกติกาได้ `bad_team` (`PROTOCOL_VERSION` 3)
- แต่ละคนเลือกแค่แม่ทัพกับรองแม่ทัพ (การ์ดสองใบที่ต่างกัน ไม่ใช่ธงยึดป้อม) ผ่านฟังก์ชันเดียว `pvpSetup()` ใน `packages/protocol` เพราะกติกาการจัดทัพกำลังออกแบบใหม่ เปลี่ยนที่จุดเดียวได้
- ไม่มีการสับมือในห้องเพื่อน (v1)
- ไม่มีรางวัลและไม่เปลี่ยนอันดับ
- เจ้าของห้องเป็นฝั่ง 0 (ซ้าย) ผู้มาเยือนเป็นฝั่ง 1 (ขวา) ผู้มาเยือนเห็นปราสาทตัวเองอยู่ขวา

## 3. ขั้นตอน
1. ล็อบบี้ → ปุ่ม **ศึกกับเพื่อน** (ถ้าต่อเซิร์ฟเวอร์ไม่ได้ ปุ่มกดไม่ได้และบอกเหตุผลเป็นภาษาไทย)
2. หน้าห้อง: ใส่ชื่อในศึก แล้ว **สร้างห้อง** หรือใส่รหัสแล้ว **เข้าห้อง**
3. ในห้อง: รหัสห้องตัวใหญ่ + ปุ่มคัดลอก, ช่องของสองฝ่าย (ชื่อ แม่ทัพและรอง พร้อมหรือยัง), เลือกแม่ทัพและรอง, ปุ่ม **พร้อม** และ **ออกจากห้อง** เจ้าของห้องมีปุ่ม **ให้ออกจากห้อง** บนช่องผู้มาเยือน (ถามยืนยันก่อน คนที่ถูกให้ออกกลับเข้าห้องนั้นอีกไม่ได้)
- **ทัพของเพื่อนก่อนเริ่ม:** ข้อความ `room` ส่งทัพเต็มเฉพาะช่องของผู้รับเอง ช่องของเพื่อนมีแค่แม่ทัพกับรอง (หน้าห้องเขียนว่า "ทัพของเพื่อนจะเปิดตอนเริ่มศึก") ทัพเต็มของทั้งสองฝ่ายเปิดใน `start`
- **เปลี่ยนทัพ = ยกเลิกพร้อมทั้งสองฝ่าย:** ใครส่ง `team` ใหม่ ทั้งสองช่องกลับเป็นยังไม่พร้อม คนที่กดพร้อมไปแล้วจึงไม่ถูกเปลี่ยนทัพแก้ทางโดยไม่รู้ตัว
4. ทั้งสองฝ่ายพร้อม → หน้าประชัน 2 วินาที → ศึก → หน้าจบ (ปุ่มหลัก: ศึกกับเพื่อนอีกครั้ง)
- **Esc:** ในห้อง = ออกจากห้อง, หน้าห้องยังไม่เข้าห้อง = กลับล็อบบี้, ในศึก = เปิดเมนู (ศึกไม่หยุด) มี "ยอมแพ้และออก" ซึ่งถามยืนยันก่อน แล้วนับเป็นแพ้ทันที (`quit.ts` ชนิด `online`)

## 4. รหัสห้องและตัวตน
- รหัส 6 ตัวจากชุด `23456789ABCDEFGHJKMNPQRSTWXYZ` (ไม่มี 0/O, 1/I/L, U/V) สุ่มด้วย `crypto.randomInt` พิมพ์เล็กหรือมีขีดได้
- ห้องที่ยังไม่เริ่มปิดเองใน 10 นาที เจ้าของห้องออก = ปิดห้อง ผู้มาเยือนออก = ช่องว่าง
- ตัวตนแบบแขก: เซิร์ฟเวอร์ออก token สุ่ม 32 ไบต์ (base64url) เก็บแค่ SHA-256 ของ token ไม่มีข้อมูลส่วนตัว ชื่อในศึกใช้ได้แค่ตัวอักษร (รวมไทย) ตัวเลข ช่องว่าง `_` `-` ไม่เกิน 16 ตัว
- ตอนนี้เก็บในหน่วยความจำ (process เดียว) **M1:** แขกย้ายไป PostgreSQL, registry ห้องไป Redis (ไม่ใช้ SQLite)

## 5. Netcode: lockstep ที่เซิร์ฟเวอร์คุม
- เซิร์ฟเวอร์รัน `createBattle(seed, pvpSetup(ทัพ0), pvpSetup(ทัพ1), { normalized: true })` ที่ 20 Hz เป็นผู้ตัดสิน
- ทุก tick ส่ง `frame { tick, cmds }` ให้ทั้งสองฝ่าย client เดิน sim ของตัวเองเฉพาะ tick ที่ได้ frame แล้ว (`Lockstep` ใน `packages/protocol`)
- client ส่งคำสั่ง `{ tick: tick ล่าสุดที่เดินแล้ว + 3, c }` (input delay 3 tick = 150 ms)
  - ถึงก่อนเวลา: รันที่ tick นั้น
  - ช้าไม่เกิน 10 tick: รันที่ tick ถัดไป
  - ช้ากว่านั้น `late`, ล่วงหน้าเกิน 40 tick `too_early`
- **ตรวจคำสั่ง:** ฝั่งต้องเป็นของผู้ส่ง (`wrong_side`), ใบต้องอยู่ในมือ (`not_in_hand`), ไม่เกิน 2 คำสั่งต่อ tick และ 6 ต่อวินาที (`too_many`); ปราณ เขตอัญเชิญ จำนวนครั้ง และปืนบรรจุ ตรวจด้วย sim เอง: ลองคำสั่งบนสำเนา state ถ้ามี event `error` ก็ไม่ใส่ใน frame (`sim`) frame จึงมีแต่คำสั่งที่มีผลจริง
- **ตรวจ desync:** client ส่ง `battleHash` ทุก 100 tick (5 วินาที) และตอนจบ ถ้าไม่ตรงกับของเซิร์ฟเวอร์: บอก client นั้น (`desync`) ผลของเซิร์ฟเวอร์ยังเป็นผลจริง และแมตช์ถูกติดธง `flagged` (matchmaking.md §8)
- **หลุด:** รอต่อกลับด้วย token 20 วินาที ต่อกลับได้จะได้ `start` พร้อม frame ที่ผ่านมาทั้งหมด แล้ว client เดินตามทัน เกินเวลา = ยอมแพ้ (`forfeit`)
- **จบ:** ผลของเซิร์ฟเวอร์เป็นผลจริง บันทึกเป็น `MatchRecord` (= `BattleRecord` + ชื่อ + ผล) ที่ `replayBattle()` รันซ้ำได้ hash เดียวกัน (ยกเว้นแมตช์ที่ยอมแพ้ ซึ่งหยุดก่อน sim จบ) `REPLAY_DIR` เขียนเป็นไฟล์ JSON

## 6. ข้อความ (protocol v1)
- client → server: `hello`, `create`, `join`, `team`, `ready`, `leave`, `kick`, `cmd`, `hash`, `ping`
- server → client: `welcome`, `room`, `start`, `frame`, `reject`, `peer`, `desync`, `end`, `error`, `pong`
- ทุกข้อความตรวจด้วย schema ทั้งสองทาง: ชนิดไม่รู้จัก ฟิลด์เกินหรือขาด ชนิดข้อมูลผิด ขนาดเกิน (client 1 KB, server 256 KB) ถูกปฏิเสธทั้งข้อความ เซิร์ฟเวอร์ปิด socket ที่ส่งข้อความผิดรูป

## 7. ความปลอดภัย
ผลตรวจและสถานะแต่ละข้อ: [reviews/pvp-security.md](../design/reviews/pvp-security.md)
- **การเชื่อมต่อ:** รับ WebSocket เฉพาะ origin ที่อนุญาต (ค่าเริ่ม: หน้าจาก localhost พอร์ตใดก็ได้, ตั้ง `ORIGINS` ได้) ไม่มี Origin = client ที่ไม่ใช่เบราว์เซอร์
  - เซิร์ฟเวอร์ไม่ยอมเริ่ม ถ้า `HOST` ไม่ใช่ loopback แต่ไม่ได้ตั้ง `ORIGINS`
- **TLS:** ตัดที่ reverse proxy หน้าเซิร์ฟเวอร์ ผู้เล่นต่อด้วย `wss://` เท่านั้น ส่วนช่วง proxy ถึงเซิร์ฟเวอร์เป็น `ws://` ในเครือข่ายภายใน
  - client รุ่น release ไม่ต่อ `ws://` เลย (build ล้มถ้า `VITE_GAME_SERVER` ขึ้นต้นด้วย `ws:` และ `net.ts` ปฏิเสธตอนรัน) ส่วน dev ใช้ `ws://` ได้เฉพาะเครื่องนี้
- **ที่อยู่ของผู้เล่น:** `TRUST_PROXY` = ที่อยู่หรือ CIDR ของ proxy ตัวจริงเท่านั้น (ค่าเริ่ม: ไม่เชื่อใคร) จึงปลอม `X-Forwarded-For` ไม่ได้
  - ตัวจำกัดทุกตัวที่นับ "ต่อ IP" ใช้ IPv4 ตรง ๆ และ IPv6 นับทั้ง /64 ผ่านฟังก์ชันเดียว (`ipKey`)
- **ตัวจำกัดต่อ IP:**
  - socket 8 (นับก่อน upgrade จึงไม่มี race คืนเมื่อ TCP ปิด)
  - socket ใหม่ 5 ทันที แล้ว 2/วินาที
  - สร้างห้อง 5/นาที, เข้าห้อง 10/นาที, แขกใหม่ 10/นาที
  - ข้อความ 30/วินาที ต่อ socket
- **ตัวจำกัดรวมทั้งเซิร์ฟเวอร์:** socket 2,000, ห้อง 1,000, แขก 5,000, รหัสห้องผิดรวม 600/นาที (หมดแล้วปฏิเสธการเข้าห้องทุกครั้ง รวมรหัสถูก จนเติมใหม่)
- **เดารหัสห้อง:** ผิด 5 ครั้งติดต่อกันปิด socket, เจ้าของห้องเตะผู้มาเยือนได้ (`kick`) และคนที่ถูกเตะเข้าห้องนั้นอีกไม่ได้ รหัสยาว `CODE_LEN` = 6 ตัว
- **socket ที่เงียบหรือช้า:**
  - ไม่ส่ง `hello` ใน 5 วินาที = ปิด
  - ping ทุก 15 วินาที ไม่ตอบ 2 ครั้ง = ตัด (ในศึก = เริ่มนับเวลาต่อกลับ 20 วินาที)
  - แขกที่ไม่อยู่ในห้องและเงียบ 10 นาที = ส่งออก (`idle`)
  - client ที่ไม่อ่านจนค้างส่งเกิน 1 MB = ตัด แล้วต่อกลับมารับประวัติใหม่ทั้งก้อน (ข้าม frame ไม่ได้เพราะจะ desync)
- **ต่อกลับ:** 3 ครั้งทันที แล้ว 1/วินาที ต่อ token ประวัติ frame ใน `start` serialise ครั้งเดียวต่อการเปลี่ยน
- **อื่น ๆ:** `/health` ตอบแค่ `{ok:true}`, เวลาในศึกใช้ `performance.now()` (เฉพาะเซิร์ฟเวอร์ `packages/sim` ไม่มีนาฬิกา), รีเพลย์เขียนแบบ async เก็บไม่เกิน `REPLAY_MAX` ไฟล์ (ค่าเริ่ม 10,000 ลบไฟล์เก่าสุดก่อน)
- **image:** multi-stage, bundle ด้วย esbuild, runtime มีแค่ dependency ของเซิร์ฟเวอร์ รันด้วย `node` base ตรึงด้วย tag และ digest, compose: `cap_drop: ALL`, `no-new-privileges`, จำกัดหน่วยความจำและจำนวน process, healthcheck, filesystem อ่านอย่างเดียว
- **M1:** แทน token ระยะยาวใน `hello` ด้วย ticket ใช้ครั้งเดียวตาม ADR 0003 (frame ที่ถูกดักไปใช้ซ้ำไม่ได้) และใส่ CSP เข้มที่ client (`connect-src` เฉพาะเซิร์ฟเวอร์เกม) กัน XSS ขโมย token จาก sessionStorage

## 8. เวลาที่วัดได้ (loopback, `packages/game/test/timing.test.ts`)
- tick ของเซิร์ฟเวอร์ช้ากว่ากำหนด: p50 0 ms, p99 10 ms
- ระยะห่าง frame ที่ client: p50 49.9 ms
- RTT p50 0.5 ms
- คำสั่งทุกใบถึงก่อน tick ที่ประทับไว้ (เหลือ 3 tick เต็ม) ไม่มีใบไหนถูกเลื่อน
- **ยังไม่ได้วัด:** เครือข่ายจริง (ping 30–120 ms) ซึ่งจะบอกว่า input delay 3 tick พอหรือต้องปรับตาม ping

## 9. รัน
- เซิร์ฟเวอร์: `npm run dev:server` (ws://localhost:8787/v1/ws) หรือ `docker compose -f infra/docker-compose.yml up --build`
- client: `npm run dev` แล้วเปิดสองแท็บ (token เก็บใน sessionStorage แต่ละแท็บจึงเป็นแขกคนละคน ถ้าโหลดแท็บใหม่กลางศึก กดศึกกับเพื่อนภายใน 20 วินาทีก็ต่อกลับเข้าศึกเดิมได้)
- เทสต์: `npm test` (protocol, ห้อง, ทั้งแมตช์ผ่านห้อง, เวลา), ภาพ: `npm run shots:pvp`

## 10. ยังไม่ทำ
- ยอมแพ้ได้หลัง 60 วินาที (ui-flow.md §2.3): ตอนนี้ออกได้ทันทีและนับเป็นแพ้
- สับมือก่อนศึก, ดูรีเพลย์ห้องเพื่อนในเกม, ผู้ชม
- ปรับ input delay ตาม ping, version gate ของข้อมูลเกม (ตอนนี้ข้อมูลไม่ตรงจะเห็นเป็น desync)

## 11. ก่อนเปิดแรงค์
ห้องเพื่อนรับได้ เพราะเล่นกับคนรู้จัก ไม่มีรางวัลและไม่มีอันดับ แต่ทั้ง 4 ข้อนี้ต้องเสร็จก่อนเปิด ranked หรือ matchmaking กับคนแปลกหน้า

1. **ข้อมูลที่ควรซ่อน (M3)**
   - ตอนนี้ `start` ส่ง `seed` และทัพของทั้งสองฝ่าย สตรีมสุ่มแจกไพ่คือ `seed ^ ค่าคงที่` และ `s.hands` เก็บมือทั้งสองฝ่าย (`battleHash` คลุมด้วย) client จึงต้องถือมือคู่แข่ง
   - client ที่ดัดแปลงจึงเห็นมือคู่แข่ง ผลสับมือ และจำลองอนาคตได้ทั้งหมด (maphack ของ lockstep)
   - ต้องตัดสินก่อนว่าเกมนี้เป็นเกมข้อมูลเปิดหรือไม่:
     - เปิด: เขียนลง GDD และ esports.md ว่าเห็นมือคู่แข่งได้ แล้วแสดงให้ทุกคนเห็นเท่ากันในเกม จะได้ไม่มีใครได้เปรียบจากการโกง
     - ซ่อน: เก็บ seed แจกไพ่ของแต่ละฝ่ายไว้ที่เซิร์ฟเวอร์ ส่งให้ client แค่มือตัวเอง เปิดใบของคู่แข่งตอนลง และแยก hash เป็นส่วนสาธารณะกับส่วนลับรายฝ่าย
   - ถ้าซ่อน แปลว่าต้องแก้ `packages/sim` จึงต้องมี spec และ golden ใหม่
2. **เลือกทัพแบบไม่เห็นกัน (M4)**
   - ทำแล้วบางส่วน: ข้อความ `room` ไม่ส่ง 4 ใบที่เลือกของเพื่อน (แค่แม่ทัพกับรอง) และการเปลี่ยนทัพยกเลิกพร้อมของทั้งสองฝ่าย (§3)
   - ที่เหลือ: แม่ทัพกับรองยังเห็นกันก่อนล็อก และเซิร์ฟเวอร์เป็นผู้ถือทัพ ผู้เล่นจึงยังเลือกแม่ทัพแพ้ทางได้ และต้องเชื่อเซิร์ฟเวอร์ว่าไม่ได้เปิดทัพให้อีกฝ่าย
   - ก่อนเปิด ranked ยังต้องทำ: เลือกแบบไม่เห็นกันทั้งทัพ (แม่ทัพและรองด้วย) ด้วย commit-reveal เต็มรูป (ส่ง hash ของทัพก่อน เปิดทัพตอนทั้งสองฝ่ายล็อก) และใน matchmaking ไม่มี "เจ้าของห้อง" ที่ต้องเลือกก่อน
3. **ข้าม input delay (L2)**
   - คำสั่งที่ประทับ tick ย้อนหลังได้ถึง 10 tick ยังรับและรันที่ tick ถัดไป
   - client ที่ดัดแปลงจึงประทับ tick ที่เดาว่าเป็นของเซิร์ฟเวอร์ และได้เปรียบเวลาตอบสนองราว 100–150 ms เหนือ client ปกติที่ประทับ tick ล่าสุด + 3
   - ranked: ใช้ `slack` ของแต่ละคำสั่ง (เซิร์ฟเวอร์เก็บอยู่แล้ว) เป็นสัญญาณกันโกงรายผู้เล่น ติดธงคนที่ slack ใกล้ 0 หรือติดลบสม่ำเสมอ (matchmaking.md §8)
   - ทางเลือก: บังคับให้ tick ที่ประทับไม่น้อยกว่า frame ล่าสุดที่ส่งให้ผู้เล่นนั้น + `INPUT_DELAY` − ค่าเผื่อ
4. **ธง desync ของฝ่ายเดียว (L3)**
   - hash ผิดครั้งเดียวจากฝ่ายใดก็ทำให้ทั้งแมตช์ `flagged` ตอนนี้ไม่มีผลอะไร
   - ranked: ห้ามให้ธงที่ฝ่ายหนึ่งยกขึ้นมาโมฆะหรือลดความแพ้ของฝ่ายนั้น บันทึกว่าฝั่งไหน hash ไม่ตรง แล้วลงโทษหรือตรวจที่ฝั่งนั้น ผลของเซิร์ฟเวอร์ยังเป็นผลจริงเหมือนเดิม
